## 3. 启动与运行依赖

run_demo.sh 的实际顺序：

1. 解析地图与启动参数；默认 P12_env1 缩放 0.5、P12_env2 缩放 0.7。
2. 未显式指定后端时添加 planning_backend:=mode_path_v2。
3. 加载 ROS Noetic。
4. catkin_make 构建当前 `catkin_ws`，加载其环境。
5. 使用当前仓库工作空间内的公共包和地图服务。
6. roslaunch fwis_v3_demo demo.launch，启动 ROS 节点。

运行依赖包括 ROS Noetic、本仓库 `catkin_ws/src` 中的 fwis_common 和 fwis_map_server、Python 数值计算依赖，以及使用相应优化功能时的 CasADi/求解器。planner 的 CMakeLists 显式依赖 fwis_common；地图发布、场景提示、停车线节点也已在本仓库。当前构建缓存已清理后重建，CMake 检测到的 workspace underlay 只有 `/opt/ros/noetic`。

## 4. ROS 节点和消息

```text
/map、/initialpose 或 /start_pose、/move_base_simple/goal
                     ↓
           fwis_v3_planner（C++）
                     ↓
       /plan/seed + /plan/seed_candidates
                     ↓
          fwis_v3_optimizer（Python）
                     ↓
       /plan/timed_trajectory + /plan/quality_report
                     ↓
          fwis_v3_playback + RViz
```

| 节点/文件 | 主要职责 |
|---|---|
| planner_node.cpp | 地图/起终点接收、路线引导、多模式动作搜索、方向与辅助候选、粗路径输出 |
| optimizer_node.py | ROS 参数和消息适配、后端分流、旧流程编排、轨迹和诊断发布 |
| playback.py | 按定时轨迹插值显示车辆、朝向和 HUD，不负责搜索或路径优化 |
| demo.launch | 启动上述节点与地图/显示节点，加载参数并应用显式覆盖 |

重要消息：Pose 是车体中心位姿；ModePrimitive 模式编号 0=A、1=O、2=Spin；PlanSeed 携带起终点及动作序列；PlanSeedCandidates 携带带来源的辅助序列；TimedTrajectory 携带时间、中心位姿、速度和模式。辅助 seed 是待审核初值，不是可直接执行路径。

RViz 同时可看到粗路径、最终路径、模式条和车体框。最终发布轨迹与粗搜索输出不是同一层结果。

## 5. 三个后端：真正分流发生在哪里

三个后端共用 planner 和 OptimizerNode。OptimizerNode.on_seed() 在约 958 行检查后端：v1/v2 调用 run_mode_path() 后 return；legacy 才继续后面的大段旧处理流程。

```text
optimizer_node.py / on_seed()
  ├─ mode_path_v1 → run_mode_path → ModePathMaster，continuous_motion_v2=False
  ├─ mode_path_v2 → run_mode_path → ModePathMaster，continuous_motion_v2=True
  └─ legacy      → 旧流程：局部修复/固定模式优化/可选 joint_refine/旧输出流程
```

因此：不是三份完全隔离的程序，也不是 v1 跑完接着 v2 再接 Bonmin。v1 与 v2 共用大量新后端代码，通过连续表示开关区分；legacy 和新后端又共用 core.py 中的一部分基础函数。

### legacy

历史基线后端。包含旧局部几何优化、固定模式优化、锚点/模式邻域，以及可选 Bonmin 联合优化。joint.enabled 默认 false。Bonmin 的模型在 core.py 的 joint_refine() 中：在初值走廊及有限段数内，共同选择分段 A/O/Spin、方向、位姿、距离与控制量，再独立重放审核。

旧 Bonmin 是真实存在的混合整数求解代码，但其恒定动作模型、加权代价和时间处理不等于当前 v2 连续模型及最短执行时间目标。不能将“求解器叫全局求解器”写成“整个地图的模式—路径—时间全局最优”。

### mode_path_v1

R02 开始的新候选主问题框架。围绕恒定动作原语做结构候选生成、几何优化、重定时和共同审核。使用 ModePathMaster，但不启用 v2 连续表示。保留作对照，不是目前默认开发主线。

### mode_path_v2

当前默认。使用相同 ModePathMaster，启用 ContinuousPlan。主流程包括：

1. 接收前端主 seed 和辅助 seed，检查动作规则。
2. 连续化、端点/模式边界拟合，保留已认证几何或执行候选。
3. 有限窗口结构编辑、精确 A 连接、可移动角点、多处 Spin 组合替换等。
4. 对每个候选连续重定时并独立审核。
5. 当前默认 minimum_time：在完整认证候选中选择实际执行时间最短者，近乎等时再比较综合质量。
6. 发布定时轨迹、报告和显示数据。

v2 尚未接入全程模式—路径—时间联合 MINLP。其连续 NLP 只调整固定结构内的控制；默认 minimum_time + mode_switch_only 下会跳过该固定结构 NLP，因为固定段长/模式/Spin 角时，曲率变形基本不能缩短时间。端点拟合、连续化以及其他局部数值求解仍可能运行，不能把这一跳过解释成“v2 完全没有数值优化”。

## 6. Python 模块分工

目录：catkin_ws/src/fwis_v3_optimizer/src/fwis_v3_optimizer。

| 文件 | 实际职责 | 归属与注意点 |
|---|---|---|
| core.py | Pose/Action/Grid、精确动作重放、车体几何、走廊、旧局部优化、joint_refine、旧时间采样 | 基础代码和 legacy 算法混在一起，v2 仍导入其基础与部分修复函数，不能整体删除 |
| mode_master.py | 新后端主问题、候选生成/预算/排序/筛选、执行可行解保留与最终选择 | v1/v2 共用；约 2310 行，职责过多 |
| continuous_geometry.py | ControlKnot/MotionBlock/ContinuousPlan、连续积分、控制过渡、边界/终点/末段拟合 | v2 连续几何核心 |
| continuous_optimizer.py | 固定模式、方向、块长的局部连续控制 NLP，IPOPT 优先、缺少依赖时有 SciPy 回退 | 不是混合整数联合规划器 |
| retiming.py | MotionLimits、恒定原语重定时、PrimitiveTimingCache | v1 与共享限值/时间工具；部分代理用于候选排序 |
| continuous_retiming.py | 连续几何的平移相位、加减速、Spin、换模和时间轨迹 | v2 最终时间计算 |
| quality.py | 车体距离、严格连续几何检查、独立时间/动态检查、方向合同、质量指标 | 新后端共同审核与评价 |
| geometry_incumbent.py | 保存认证几何快照，在执行失败时提供几何证据 | 几何通过不冒充执行通过 |
| legacy_geometry_provider.py | 有界借用旧锚点、局部修复和固定走廊几何，再送共享审核 | 不调用整条 legacy 流程，也不代表调用 Bonmin |
| planning_display.py | 显示站点等辅助处理 | 显示与安全审核有不同采样用途 |
| diagnostics.py | 诊断文件的原子写入 | 基础工具 |

截至本次检查：optimizer_node.py 约 2861 行、core.py 约 4080 行、planner_node.cpp 约 2122 行。当前的问题是分层和依赖边界混合，文件名不足以说明算法归属。

## 7. 配置归属

params.yaml 被加载到 planner、optimizer 和 playback 各自节点命名空间；各节点读取自己需要的部分。run_demo.sh 设置默认后端；demo.launch 的显式参数在加载 YAML 后覆盖相应字段。直接启动 launch、通过 run_demo.sh 启动、以及指定其他 config_file 可能得到不同配置，要记录实际运行参数。

| 配置部分 | 用途 |
|---|---|
| planning | 后端、方向、不揉库规则 |
| quality.limits | 新后端执行 profile、目标速度、加速度、换模策略等 |
| quality.cost | 新后端共同评价指标权重；默认最短时间时不是所有指标都作为主选路目标 |
| quality.search | ModePathMaster 新后端搜索与审核预算，v1/v2 使用 |
| search | C++ 前端格点、步长、启发式/恢复/方向搜索等 |
| vehicle / collision | 车辆、安全尺寸增量和碰撞采样合同，多个模块读取 |
| cost | 前端/旧动作代价相关；与 quality.cost 不是同一个目标函数 |
| joint | legacy 的 Bonmin 参数；不会因为存在该节就让 v2 调用 MINLP |
| mode_master（顶层） | legacy 局部模式邻域相关，不能等同 quality.search |
| optimization / repair / endpoint_replan / time | 旧流程或相应修复、采样功能参数，需追踪具体读取点 |
| visualization | 诊断区域显示开关 |

默认 params.yaml 使用 kinematic_sim_mode_switch_only_v2：2 m/s，换模 0.3 s，同模式不因曲率限速，起停仍受加速度/jerk 影响。params_restricted.yaml 保留受限运动对照。两种 profile 的动态声明不同，结果不能混作实车全限制认证。

某些注释仍保留早期 R03 或旧方向限制描述，应以当前读取代码、运行配置与报告为准；整理时应更新，不能依据注释把旧功能误判为当前默认行为。

## 8. 已验证能力与未完成目标

R20 当前源码七个冻结 ROS 输入都通过实际发布、5 mm 整车扫掠、2 cm/1° 终点、当前 profile 动态/方向以及速度/显示审核。最新截图任务执行 53.845→35.119 s，换模 11→5；仍有两个内部 Spin 和一个末端 Spin；后端单次 8.350→14.596 s。其余六组执行时间与 R19 一致。

这证明有限任务上的候选质量和发布链可复核，不证明任意输入成功或全局最优。R12 的 15 输入及受限 profile 历史验收，也不能直接算成当前 R20 的完整跨图复测。

未完成的核心目标是：在当前 v2 共同模型中，将模式、方向、段长、边界位姿、切换位置、连续控制和执行时间共同建模求解，并保留整车独立审核。旧 Bonmin、固定结构 NLP、局部候选搜索都不能单独视为该目标已完成。

## 9. 使用 Git 时建议固定的边界

本次不创建仓库、不提交、不移动或删除历史文件。先在本机确认 .git 的实际可写/有效状态；当前环境看见只读目录，且 git 未识别出仓库。

建议一个仓库管理当前项目；后端选择是运行配置，不必为 legacy/v1/v2 各维护一个长期分支。先提交当前可复核源码作为基线，之后再做重构和联合规划。建议为当前基线打明确标签（例如 baseline-r20），为联合模型开发单独功能分支（例如 feature/joint-planning），通过提交记录和标签取代 before/反复复制整份源码。

建议提交：run_demo.sh、catkin_ws/src、tests、tools、实际使用的地图及其元数据、必要文档、依赖与构建说明、精简冻结案例和基准汇总。检查地图来源与大型研究资料的存储方式。

建议排除：catkin_ws/build、devel、install、Python 缓存、根 build、生成日志、临时运行结果、大量重复源码快照、凭据目录 .aws。relust 不宜一次整体提交；先保留其外部归档，再挑选小型案例清单、指标 JSON、源码指纹、关键图片作为版本化证据。对 .codex/.agents 等环境配置逐项检查，避免无选择提交个人配置或凭据。当前 .gitignore 仅覆盖 catkin 生成目录与 Python 缓存，尚不足以直接 git add 全目录。

## 10. 后续整理建议：目标结构，不是当前实现

第一步做不改变算法行为的拆分：

- ROS 适配层只负责参数、订阅、后端选择、发布。
- 后端接口统一输入地图/起终点/限值/预算，输出轨迹、认证状态、报告。
- legacy 后端独立封装，保留基线能力。
- v1 保留明确对照入口；v2 作为当前开发主线。
- 基础运动学、几何、碰撞、时间规划、认证独立共享，移出 core.py 的混合职责。
- 新联合模型作为明确模块接入 v2，区分建模、求解、真实重放与审核，报告实际调用与采用情况。
- 运行产物按 Git commit + case + profile 记录；配置拆出公共部分与后端专属部分。

不要把目录重命名与算法更改混在一个提交里。先以现有七组冻结结果作为回归基线，再逐步拆分；新增联合能力独立提交，并用同输入/预算/profile 对照。一次只改变文件组织时应保持轨迹及审核结果一致。
