## 1. 接手时先知道的情况

当前 `bash run_demo.sh --map P12_env4` 默认运行 `mode_path_v2`，不是 legacy。它是独立的连续控制原型后端，尚未完成稳定的多地图验收。用户反复反馈：中段无理由减速甚至约 0.01 m/s 爬行、规划慢、部分任务无解、轨迹和模式搭配奇怪，整体体验不如 legacy。

**用户在本次交接新增的问题：安全走廊的框比车还小，航向也不对。** 此问题尚未做对应手测消息的逐点复现；本次源码核对已确认，当前可视化把四个车体覆盖圆的“圆心可移动区域”直接画成小矩形，并称为走廊包络。它们本来就可能小于车体，不能当作包围整车的自由空间框。v2 中这些框是在轨迹优化完成后才生成的，未约束连续 NLP。这是首要交接问题，详见第 5 节。

现有小规模探针说明部分案例可运行，不代表架构已经实现模式与路径的全局联合优化，也不代表新版本整体优于 legacy。**v2 尚未接入 Bonmin 全局/段级 MINLP。** `--joint on` 或旧的 `joint.enabled` 不能自动让 v2 走旧 MINLP 流程。

最近算法改动止于 R07 的连续控制初始化、碰撞审计顺序和粗边 sweep 缓存。本次交接只更新文档并保存源码指纹，没有继续改算法、修改地图或运行新的 ROS/单元测试。

## 3. 当前真实算法架构

```text
ROS 地图、车辆中心起点和真实目标
  ↓
C++ planner_node.cpp
  多个净空权重的二维位置 A* 路线
  → 自适应路线锚点上的有限 A/O/Spin 连接器和模式图
  → 有界 Hybrid A* 改进和候选竞争
  → 只发布一个选中的 PlanSeed（离散动作序列）
  ↓
Python optimizer_node.py 按 backend 分流
  ├─ legacy：固定走廊 NLP、锚点/局部模式提议、修复、经验证粗路回退
  │           → mode+gear 分组 smoothstep 时间采样 → SAT 复验
  ├─ mode_path_v1：常值动作与静止重配置时间模型（历史后端）
  └─ mode_path_v2：ModePathMaster
       连续 A 曲率/O 斜移角表示
       → 控制平滑、端点投影
       → 有限局部模式/方向/上游航向结构提议
       → 固定拓扑连续几何 NLP 原型
       → 速度、加速度、jerk、轮系约束重定时
       → 整车 5 mm sweep、动态、方向、终点独立审核及质量评分
       → 选 winner，再构建显示走廊
  ↓
/plan/timed_trajectory、路径、模式色带、质量报告、走廊 Marker
  ↓
playback.py 按已发布时间戳插值，显示 ego 和速度；它不独立重定时
```

### 3.1 车辆与连续运动合同

车辆物理长 `0.738 m`、宽 `0.500 m`、轴距 `0.494 m`、轮距 `0.364 m`，最小 A 转弯半径参数 `0.81 m`。规划起点、目标和输出均为车辆中心，yaw 单位为弧度，x/y 为米。

`ContinuousPlan` 包含有序 `MotionBlock`，模式编号 A=0、O=1、Spin=2。平移块方向为 ±1，按非负弧长 s 参数化：

- A：`dx/ds=d·cos(theta)`、`dy/ds=d·sin(theta)`、`dtheta/ds=d·kappa(s)`；控制为中心曲率。
- O：`dx/ds=d·cos(theta+phi(s))`、`dy/ds=d·sin(theta+phi(s))`，块内车体 `theta` 保持不变；控制为斜移角。**车体航向与路径切线可以不同。**
- Spin：中心不平移，改变 yaw；中心平移速度 v 为 0。

A/O 控制使用 C1 Hermite 曲线，控制节点不应被当成停车事件。内部 yaw 可不 wrap；显示四元数周期化。`TimedPoint.v` 是有符号中心平移速度，负值代表倒车。不能将负速度改成正值掩盖倒车。

### 3.2 模式选择尚未联合完成

C++ 内部比较多条路线，但 `PlanSeed.msg` 只携带一个动作序列。Python 外层有有限结构编辑，能产生不同模式词；连续 NLP 子问题仍固定模式/方向词、块长和切换位置，主要调整局部控制。它不是“每个站点都有模式变量的全局路径/时间 MINLP”。

更严重的是，连续 NLP 改善后的 `ContinuousPlan` 和原来的 `actions` 同时保存在候选中，下一轮结构提议仍主要从旧 `actions` 出发。几何优化没有可靠反馈到模式搜索。`mode_master.py` 中还存在放入 `pending`、却被 v2 分支排除后续 whole-path NLP 的提议。这是覆盖不足和空候选池难恢复的关键。

## 5. 新问题：安全走廊框尺寸和航向错误（最高优先级）

### 5.1 已从源码确认的事实

1. `core.py:509–519` 用四个圆保守覆盖车体，每个圆中心位于车身纵轴不同位置。`build_corridors():604–662` 对每个圆心构造可移动区域，返回每个位姿四个框，结构为 `(cx,cy,half_long,half_lat,reference_yaw)`。
2. 这些框是圆心的配置空间约束区域，不是整车外框。构建先按圆半径腐蚀自由空间，再把世界 AABB 内接为参考航向矩形。窄道或斜向下会缩小，可能远小于 0.738×0.500 m。当前 `publish():2471–2538` 直接逐一画这四个框，却使用 `v3_corridor_envelopes` 名称及“走廊包络”解释，语义错误。
3. v2 在 `run_mode_path():2373–2393` 从获选连续轨迹采样，再构建这些框。报告明确写 `role=final_geometry_envelope`、`used_in_continuous_nlp=False`。安全来自独立 whole-body sweep；当前“显示框非空”不能证明优化使用了安全走廊。
4. 任一 feature 无法建立完整 disc 区域时，会回退到 point 区域；返回只有全局 `covered` 标志，没有逐 station/feature 的认证类型。显示时整个 mixed 分支都着琥珀色，无法说明哪个框具有整车覆盖条件，哪个只是点提示。
5. `Grid` 的尺寸膨胀为 `(length+margin)/2` 和 `(width+margin)/2`；margin=0.04 意味着总尺寸各加 0.04，即单侧加 0.02。接手时必须明确 margin 的合同，不能把它误写成每侧 4 cm。
6. `replay_continuous` 首行 mode 为 `None`，v2 把它写进 `corridor_modes[0]`；完全 disc 显示分支用此模式查颜色，可能跳过首站。这是静态可见的显示遗漏，尚未做针对性复测。

### 5.2 航向问题目前的证据边界

`corridor_box_corners` 根据 box 的参考 yaw 把角点变到世界坐标；Marker 使用单位四元数，因为 points 已在世界坐标。这种做法本身正确，不能把单位四元数简单改成车体 yaw 后再重复旋转一次。

v2 box 的 yaw 来自建立框时的连续路径车体 yaw。O 模式车体 yaw 不等于运动方向；倒车运动方向也会反向。legacy 框可能仍以优化前 reference pose 定义，和最终轨迹 yaw 不完全一致。以上都是需要检查的坐标合同，不足以解释或否定用户报告的航向错误。

**尚缺这次错误框对应的 TimedTrajectory、Marker 点、backend、地图比例和起终点消息，因此不要宣称航向问题已定位或已修复。** 先从 R07 现成 case 重放，保存每个框对应的 plan_id、station、reference_pose、mode、frame、四个角点和尺寸，然后与发布轨迹/车体逐站比较。若无法复现，再采集用户实际任务消息。

### 5.3 下一执行者的具体检查与修复合同

- 明确两类数据：用于优化的配置空间 corridor；用于用户理解的物理整车 footprint/自由空间包络。分别命名和记录认证方式。不要把小圆心框强行放大到车体大小，这会破坏原有自由空间证书。
- 走廊对象改为有命名字段的 schema，含 plan_id、map hash、reference pose、station、body feature offset/radius、坐标系、认证类型和是否参与优化；少用裸五元组和靠列表索引对应。
- 检查包围整车的显示对象是否真的包含该站 footprint；配置空间圆心框则检查对应 feature center 是否在框内。两者不可使用同一个 containment 门槛。
- 逐站核验 yaw 来源、弧度单位、车体中心/轴中心、O 车体 yaw/运动切线、逆向、Spin、跨 ±π，以及 marker 的 stale/DELETEALL 行为。框朝向对齐应以明确的参考车体合同为准。
- 单独绘制一次实际车体四角与带 margin footprint，核对 playback 的 0.738×0.500 和规划车体一致；同时记录真实 marker 尺寸，不只检查 `nonempty=True`。
- 真正接入连续 NLP 的 corridor 是后续结构工作：建立受认证的自由空间/配置空间约束，NLP 消费同一个版本化对象，末尾仍独立 sweep。仅恢复一圈好看的框不能算 corridor 优化完成。
